# kairos-keeper

Standalone Rust service that permissionlessly calls the `perp` program's `liquidate` and
`update_funding` instructions — nothing else does, so without this bot underwater positions
never get closed and funding never advances. See `.docs/perp-keeper-spec.md` for the full spec.

## What it does

Two independent loops, spawned as separate `tokio` tasks, sharing one RPC client and one
keeper keypair. Neither loop stopping affects the other.

```
                ┌────────────────────────┐        ┌────────────────────────┐
                │   liquidation_loop      │        │     funding_loop       │
                │   (poll every N secs)   │        │   (poll every N secs)  │
                └───────────┬─────────────┘        └───────────┬─────────────┘
                            │                                   │
                for each configured market               for each configured market
                            │                                   │
              getProgramAccounts (memcmp on               getAccountInfo(market)
              Position.market) -> open positions                │
                            │                          due? now - last_funding_time
              fetch market + oracle price                    >= interval_seconds
                            │                                   │
              compute equity off-chain                     build update_funding ix
              (equity.rs, mirrors on-chain math)                │
                            │                                   │
              equity <= maintenance_margin?                     │
                            │                                   │
              build liquidate ix ─────────────┐                 │
                                               ▼                 ▼
                                        tx.rs::submit() -> sign, send, confirm, fetch logs
                                               │
                              Ok  -> decode PositionLiquidated / FundingUpdated, log reward
                              Err -> log + continue (lost race, stale account, RPC hiccup)
```

**Liquidation loop** (`liquidation_loop.rs`): every `LIQUIDATION_POLL_INTERVAL_SECS`, for each
configured market — fetch the market, read a fresh price from the market's `oracle` account,
scan for open positions, compute each position's equity, submit `liquidate` for any that breach
`maintenance_margin_bps`.

**Funding loop** (`funding_loop.rs`): every `FUNDING_POLL_INTERVAL_SECS`, for each configured
market — fetch the market, check `now - last_funding_time >= interval_seconds` (a field **on
the market itself**, not a keeper setting — see `constants.rs::INTERVAL_SECONDS` on-chain,
typically 3600s), submit `update_funding` if due. The keeper's poll interval only controls how
often it *checks*; the tx only fires once the market's own interval has actually elapsed.

Both loops treat rejected submissions (lost race to another keeper, stale account, RPC error)
as expected and non-fatal: log and move to the next position/market. Never panics on a
rejection.

## Module map

| File | Responsibility |
|---|---|
| `main.rs` | Load config, load keypair, spawn both loops |
| `config.rs` | `.env` parsing + validation (testable via an injected lookup function) |
| `rpc.rs` | Hand-rolled JSON-RPC client: account reads, `getProgramAccounts`, blockhash, `sendTransaction`, `getSignatureStatuses`, `getTransaction` |
| `accounts.rs` | `Position`/`SynteticMarket` structs + Anchor discriminators — **generated by `build.rs`** from the perp IDL |
| `events.rs` | `PositionLiquidated`/`FundingUpdated` structs + `find_event()` log scanner — **generated by `build.rs`** |
| `instructions.rs` | `LIQUIDATE_DISCRIMINATOR`/`UPDATE_FUNDING_DISCRIMINATOR` — **generated by `build.rs`** |
| `pda.rs` | Position/market_vault/insurance_fund_vault PDA + ATA address derivation |
| `ix.rs` | Builds the raw `Instruction` for `liquidate`/`update_funding` (no `anchor-client`; account order hand-matched to the on-chain `Accounts` structs) |
| `oracle.rs` | Reads a Pyth `PriceUpdateV2` account by fixed byte offset, replicating the on-chain staleness/confidence guards |
| `equity.rs` | `apply_funding`/`calculate_pnl`/MMR threshold — off-chain port of the on-chain math, must match exactly |
| `tx.rs` | Signs a transaction, submits it, polls for confirmation, returns `Confirmed{signature, logs}` or `Rejected{reason}` |
| `liquidation_loop.rs` / `funding_loop.rs` | The two loops described above |
| `util.rs` | `now_unix()` |
| `build.rs` | Reads `programs/perp/target/idl/perp.json`, emits the generated files above into `OUT_DIR` |

## Why some things are the way they are

- **No `anchor-client`.** This repo has no Rust client/SDK crate for `perp`. Instructions are
  built by hand in `ix.rs` (`Instruction` + `AccountMeta`), matching `kairos-indexer`'s existing
  style of talking to RPC directly.
- **No fixed oracle config.** `SynteticMarket.oracle` *is* the Pyth price-update account to pass
  into `liquidate` — read from the market itself, not supplied separately.
- **`build.rs` codegen** avoids hand-copying struct layouts/discriminators out of the on-chain
  program and re-deriving them by hand whenever `perp` changes. Scoped to only what the keeper
  touches (`Position`, `SynteticMarket`, two events, two instructions) — a focused subset of what
  `kairos-indexer/build.rs` generates for the whole IDL.

## Config (`.env`)

See `.env.example`. Required: `RPC_URL`, `PERP_PROGRAM_ID`, `USDC_MINT`, one of
`KEEPER_KEYPAIR_PATH` / `KEEPER_KEYPAIR_SECRET`. Optional: `LIQUIDATION_POLL_INTERVAL_SECS`
(default 5).

Markets are not configured — both loops discover every `SynteticMarket` account under
`PERP_PROGRAM_ID` via `getProgramAccounts` on each poll (`RpcClient::get_all_accounts`), so a
market added later with `initialize_market` is covered on the next poll with no restart.

There's no `FUNDING_POLL_INTERVAL_SECS` either: unlike liquidation, funding has an on-chain
timing signal — each market's own `funding_config.interval_seconds` (default 3600s) gates
`update_funding` (`FundingTooEarly` otherwise). Picking that cadence arbitrarily via a static
config value risks polling less often than a market's own interval and delaying its tick.
`funding_loop::run` currently sleeps a hardcoded 30s between cycles — see the `TODO` there;
it should instead derive its sleep duration each cycle from the tightest
`interval_seconds` among currently discovered markets.
Liquidation has no on-chain equivalent to sync with — how often to scan for undercollateralized
positions is purely a reaction-speed-vs-RPC-load tradeoff, which is what
`LIQUIDATION_POLL_INTERVAL_SECS` remains for.

## Running

```bash
cp .env.example .env   # fill in RPC_URL, keypair
cargo run
```

## Testing

```bash
cargo test
```

28 unit tests, all offline (fabricated data, no network): config validation, equity math
against known on-chain fixture values (from `pnl.rs`/`test_liquidate.rs`), tx builder,
PDA determinism, instruction account ordering, oracle decode/guards, funding due/not-due
boundaries.

**Not yet covered**: no RPC call has been exercised against a real node, no transaction has
actually been submitted/confirmed, and the Pyth account byte-offset parsing in `oracle.rs` has
never been checked against a real account. Devnet verification (task 6 of the spec) is a
manual next step — needs a funded keeper wallet and a manually-created underwater position.
